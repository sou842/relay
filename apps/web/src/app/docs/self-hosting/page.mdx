# Self-hosting & access

## Requirements

The gateway keeps a **permanent connection** to WhatsApp, so it needs an
always-on process. All of its data is in MongoDB, so the machine itself needs
no persistent disk: containers and redeploys keep sessions and history.
Serverless platforms (Vercel functions, Netlify, Cloudflare Workers, Lambda)
cannot run it. The web app can run anywhere Next.js runs, as long as it can
reach the gateway.

| Option | Notes |
|---|---|
| Your own PC | Simplest; works while the PC is on |
| Old laptop / Raspberry Pi | Cheap always-on box at home |
| Oracle Cloud Always Free VM | Free, always on; needs card verification |
| Google Cloud e2-micro | Free tier in some US regions; 1 GB RAM is enough |

## Reaching it from anywhere

Expose the **web app** (not the gateway) with Cloudflare Tunnel:

```bash
cloudflared tunnel --url http://localhost:3000
```

Then set `BETTER_AUTH_URL` to the tunnel URL and restart the web app.

Expose the gateway only if scripts outside your machine need the HTTP API. In
that case set `GATEWAY_PUBLIC_URL` so media links point to the public address,
and treat every instance token like a password.

## Data and backups

| Data | Location |
|---|---|
| WhatsApp sessions, message history, notification queue, media | MongoDB, gateway database (`relay_gateway`) |
| Users, sessions, instance ownership | MongoDB, web app database |

Back up both databases (Atlas backups cover them). Anyone with read access to
the gateway database can use the linked WhatsApp accounts, so keep its
credentials as private as the admin key.

Upgrading from a version that stored data in `apps/gateway/data/`? Stop the
gateway and run `npm run migrate:sqlite -w gateway` once; linked numbers keep
working without a new QR scan.
